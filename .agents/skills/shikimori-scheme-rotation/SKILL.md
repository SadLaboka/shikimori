# Каталог и автосмена Shikimori

Соблюдай [AGENTS.md](../../../AGENTS.md). Сначала выясни, нужна новая готовая
схема в каталоге, изменение расписания/публикации или восстановление после сбоя.
Устройство и настройка находятся в [scheme-rotation.md](../../../docs/scheme-rotation.md);
читай нужный раздел, не дублируй его инструкции в новых файлах.

## Подключение готовой схемы

- Цвета, изображения и сборку готовь по
  [shikimori-color-schemes](../shikimori-color-schemes/SKILL.md).
  Не считай создание CSS разрешением на включение в действующее расписание.
- Единственный каталог: `extensions/firefox/catalog.mjs`. Actions использует
  `recognize`, `nextSchemeId`, `schemeCss`; не добавляй второй список схем в runner.
  `CYCLE_ORDER` задаётся явно. Проверь, что каждая схема включена ровно один раз.
- Новая запись должна ссылаться на опубликованные проверенные байты через полный
  commit-SHA, хранить SHA256 и распознаваться после сохранения. Не менять общий
  `REVISION` ради одной новой схемы: у записи есть собственное поле `revision`.
  Сохраняй `historicalSources` и распознавание уже установленных вариантов.
- Добавь собственную сборку/проверку новой схемы в workflow ротации и выпуска
  Firefox, если существующие команды её ещё не покрывают. Проверь полный круг,
  переход со старой схемы и отказ для неизвестного CSS. Места с конкретным числом
  карточек ищи в popup, тестах, упаковщике и документации — не угадывай их устройство.
- Действующее расписание может применить новый каталог сразу после push в `main`,
  установленный XPI — только после выпуска. До push согласуй совместимый порядок:
  остановка автосмены, выпуск расширения, затем возобновление. Не выключай workflow
  и не выпускай расширение без соответствующего разрешения из текущей сессии/AGENTS.

## Логика и восстановление

- Публикация остаётся в `scripts/deploy.ps1`. Runner готовит план и хранит журнал;
  не добавляй обходной PATCH. Backup загружается до записи, кандидат закреплён SHA256,
  исходник и результат сверяются. Не сокращай эти этапы ради времени запуска.
- Облачные токены используют отдельный профиль `rotation`. Не читай credentials
  для изменения кода. OAuth, refresh, загрузка секретов и включение расписания —
  отдельные действия. Не повторно загружай локальную пару после облачного refresh.
- `pending` и `refreshPending` сохраняются **до** соответствующего необратимого
  запроса. При сбое сначала выясни результат по инструкции; не сбрасывай журнал
  и не повторяй PATCH/refresh вслепую. При обновлении кода сохраняй формат состояния
  или добавляй явную миграцию без потери этих отметок.
- Общей блокировки с прямыми запросами Firefox нет. Проверки перед PATCH уменьшают
  риск, но не гарантируют отсутствие гонки. Не обещай строгую очередь без изменения
  архитектуры расширения и сервиса.

Для runner и deploy запускай `tests/rotation.test.mjs`, `tests/rotation-deploy.tests.ps1`,
`tests/deploy.tests.ps1` и затронутые проверки Firefox; для новой схемы — её реальные
визуальные проверки. Тесты API только на подставных данных. Не выдавай их за живую
публикацию, настройку секретов или проверку расписания. В итоге перечисли готовые
изменения, проверки и оставшийся этап включения; push/публикация отдельно по
[release.md](../../../docs/release.md).

При изменении загрузчика credentials дополнительно запусти
`tests/rotation-upload.tests.ps1`: он проверяет передачу через stdin и скрытие
вывода на подставном дочернем процессе, без DPAPI-профиля и запросов GitHub.
