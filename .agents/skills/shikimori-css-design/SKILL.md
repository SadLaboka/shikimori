# Shikimori CSS design

Соблюдай [AGENTS.md](../../../AGENTS.md). При оптимизации текущий вид — эталон;
при дизайне меняй только согласованное. Skill не разрешает публикацию или push.

Для создания отдельной схемы или организации переключения используй
[shikimori-color-schemes](../shikimori-color-schemes/SKILL.md); этот навык
задаёт визуальные проверки её CSS. Для перекраски самих GIF/WebP —
[shikimori-animated-recolor](../shikimori-animated-recolor/SKILL.md).

## Контекст по необходимости

Начни с `git status`, поиска селекторов и нужного блока `styles_optimized.css`.
Читай только пересекающиеся правила основы. [Архитектура](../../../docs/architecture.md)
нужна для каскада/источников; [производительность](../../../docs/performance.md) —
для ускорения; [preview.md](../../../docs/preview.md) и
[design-workflow.md](../../../docs/design-workflow.md) — перед проверкой.
Старые отчёты и все четыре файла основы заранее не загружай.
Только анализ: без правок и браузера для статического вопроса.

## Реализация

1. Определи страницу, компонент, состояния и ожидаемые изменяемые свойства;
   при оптимизации — способ доказать сохранение поведения. Для ясной задачи
   действуй; спрашивай только о существенно разных вариантах дизайна.
2. Меняй один связный блок. Проверь специфичность, shorthand, переменные,
   media, псевдоэлементы и пересечения. Не считай `:is()`/`:where()` нейтральной
   заменой селекторов. Не исправляй соседние мобильные дефекты попутно.
3. Предпочитай собственные правила основного CSS; `vendor/` — эталон.
   Правка `css/base/` не обновляет commit-URL. Обычный owned-import путь принимает
   байты vendor; точные исключения main1/main3 имеют отдельные пилоты и манифесты
   (нужный раздел preview.md). Другим изменениям основы нужен проверяемый способ
   подстановки и версионирования, а не обход хэшей. DOM/JS сайта не меняй.
4. Подготовь кандидат в `.preview/`, проверь его, затем перенеси в основной CSS
   и сверь хэш. При ошибке повтори затронутые проверки; не оставляй недоказанный результат.

## Проверки и экономия

- Используй существующий Playwright: `--css`, `--widths 1440,390,360`,
  `--component profile|history|catalog`. Каталог/фильтры: `--component catalog --check-filters`.
  `--check-layout` — только профиль; `--url` отсутствует. Остальные страницы
  требуют своего реального DOM.
- Проверь геометрию, вычисленные стили, псевдоэлементы, применимые
  hover/focus/active, изменённые media-границы и фазы анимаций.
  Ноль мишеней — пробел покрытия; fixture не равен реальному интерфейсу.
- Строгие миграционные аудиты требуют прежнего CSSOM. При намеренных изменениях
  сохраняй их исходный FAIL, объясни конкретные причины и выполни целевую проверку
  ожидаемых отличий и остальных инвариантов. Защиты не ослабляй; область PASS указывай явно.
- При дизайне просмотри целевые снимки на трёх ширинах. При оптимизации сначала
  оцени структурную эквивалентность и поведение; снимки открывай при неоднозначности.
  GIF/WebP не замораживаются, pixel diff не является вердиктом.
- Тесты инструментов нужны при изменении их логики/инвариантов; CSS проверяй по поведению.
  Не повторяй успешные прогоны для тех же байтов без причины. Не читай все снимки
  и старые аудиты, не добавляй универсальные инструменты для одной правки.

Отчёт: что изменено и почему, визуальный результат, проверки/пропуски,
ссылки на локальные материалы. Ускорение подтверждай замером, не числом строк.
