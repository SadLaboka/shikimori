# Shikimori CSS migration

Работай от корня репозитория с учётом [AGENTS.md](../../../AGENTS.md).
Этот workflow не публикует CSS, не запускает deploy/OAuth, не читает секреты
публикации и не выполняет git push. Не добавляй MCP и зависимости без необходимости;
используй существующий предпросмотр, не создавай ему замену или сборщик ради обхода защит.

## Режим и подготовка

- При запросе «только анализ» не меняй CSS, импорты, vendor и инструменты. Разрешены
  чтение, изолированная браузерная инспекция и отчёты в игнорируемой `.preview/`.
  Заверши планом и пробелами проверки, без заявления об успешной миграции.
- Прочитай [план](../../../docs/style-migration.md),
  [предпросмотр](../../../docs/preview.md), [структурный аудит](../../../docs/layout-audit.md)
  и [аудит порядка](../../../docs/cascade-order-audit.md). Старые отчёты — свидетельства
  прежнего запуска, не доказательство текущей эквивалентности.
- Изучи актуальные `tools/preview/`, `package.json`, CLI и тесты; проверь наличие Node,
  менеджера пакетов и браузера. Не предполагая флаги или пути снимков, проверь команды.

## Анализ и перенос

1. Сопоставь исходник выбранного импорта с его реальным развёрнутым блоком
   `style#custom_css`: сохрани источник, хэш и состав правил. Определи зависимости,
   URL ресурсов, страницы, локали, состояния и фактические DOM-мишени.
2. Выбери небольшой независимый импорт/блок. Проверь селекторы, специфичность,
   `!important`, shorthand/longhand, media/layer/scope, переменные и псевдоэлементы.
   При смене позиции проверь ВСЕ пересечённые правила, включая AUTO-вставки Shikimori.
   Порядок меняй только при доказанной эквивалентности; иначе сохрани его либо остановись.
3. Подготовь временный кандидат в `.preview/` без одновременной оптимизации.
   Сохрани семантику и происхождение; не исправляй попутно старый синтаксис.
   Удалять весь импорт можно только при полном проверенном переносе его содержимого.
   Не затрагивай другие компоненты. После успешной проверки кандидата перенеси тот же
   снимок в `styles_optimized.css` и повтори соответствующие проверки.

## Доказательство результата

Проверенные точки входа (запуск из корня; снова сверяй с текущим кодом):

```powershell
pnpm --dir tools/preview test
node tools/preview/preview.mjs --check-layout --widths 1440,390,360
```

**Граница покрытия:** сейчас `preview.mjs` жёстко привязан к профилю, а `--check-layout`
и `audit.mjs` проверяют десять правил раскладки CSS-club. `audit-order.mjs` и
`make-audit-fixtures.mjs` также специализированы на этом переносе. Их PASS не проверяет
новый импорт. Не предполагая поддержки `--url`/`--component`, для нового компонента
сначала обеспечь целевую страницу и отдельный аудит: при необходимости минимально
дополни существующие средства, сохранив их защиты и тесты. В режиме анализа лишь
зафиксируй этот пробел. Без покрытия компонента не переходи к удалению импорта.

- Заменяй правила в той же таблице стилей, а не накладывай кандидат поверх старого.
  Удаляй из тестовой основы только переносимый блок, сохраняя остальные импорты.
  Проверь реальный CSSOM: происхождение/число правил, отсутствие старых и лишних копий
  во всех доступных листах, положение листа и хэш применённого кандидата.
- На затронутой странице сравни до/после: снимки, геометрию, вычисленные свойства,
  `::before`/`::after`, применимые hover/focus/active и локали. Проверь 1440, 390, 360px
  и обе стороны релевантных media-границ. Нулевое число мишеней не считается проверкой;
  искусственные примеры дополняют, но не заменяют реальный компонент.
- Запусти существующие тесты и строгий режим, если поддерживается. Для нового аудита
  проверь временной копией, что пропуск правила обнаруживается, в том числе когда
  media неактивна. Успех проверки раскладки отмечай отдельно от результата нового блока.
- Следуй механике стабилизации из документации: одинаковая пауза CSS-анимаций,
  завершённые tooltip/resize-состояния; GIF/WebP не замораживаются. Pixel diff сам
  по себе не доказывает ошибку или эквивалентность. Просмотри сохранённые снимки.
- Исправляй выявленные ошибки и повторяй затронутые проверки. При критическом сбое,
  недоступном компоненте или недоказанной эквивалентности останови перенос; не оставляй
  непроверенный кандидат в основном CSS и не объявляй PASS. Сообщи причину и следующий шаг.

## Отчёт

Укажи изменённые правила/импорты и визуальный результат; отдельно перечисли пройденные,
проваленные и невыполненные проверки, найденные проблемы и исправления, ограничения
автоматизации и риски будущего обновления внешней основы. Дай ссылки на реальные
локальные HTML-отчёты и снимки. Для анализа явно напиши, что CSS не менялся и перенос
не проверен; отсутствие снимков объясни, не подменяя их отчётом другого компонента.
