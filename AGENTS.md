
# Shikimori CSS Project

## Project
This repository contains custom CSS for a Shikimori user profile.

## Rules
- Preserve the existing visual design unless asked otherwise.
- Do not remove or change external @import rules without permission.
- Prefer minimal, targeted CSS changes.
- Consider selector specificity, cascade order and imported styles.
- Do not restructure the entire stylesheet for small fixes.
- Explain any potentially breaking changes.
- Never push to GitHub or publish to Shikimori without explicit approval.

## Verification
- Check for CSS syntax errors.
- Review affected selectors and media queries.
- Verify visual changes in a browser when possible.
- Report anything that could not be verified.

## Контекст проекта

- Пользователь общается по-русски и только начинает работать с ИИ-агентами.
  Объясняй причины изменений простым языком, без обещаний непроверенного ускорения.
- Профиль: https://shikimori.io/SadLaboka. Репозиторий публичный:
  https://github.com/SadLaboka/shikimori; основная ветка — `main`.
- Тема действует на всём Shikimori, а не только на главной странице профиля.
  Глобальные селекторы могут быть намеренными: не ограничивай их профилем автоматически.
- На сайте можно менять пользовательский CSS, но нельзя редактировать HTML и скрипты.
  Не предлагай решения, требующие изменения DOM или добавления JavaScript, как обычную CSS-правку.
- Текущий внешний вид — эталон. Сохраняй изображения, анимации, цвета и композицию,
  если пользователь отдельно не согласовал изменения.

## Особенности Shikimori и CSS

- Shikimori предварительно обрабатывает CSS: в изученной странице содержимое внешних
  импортов было развёрнуто в `<style id="custom_css">` перед собственными правилами.
  Поэтому наличие `@media` перед `@import` в исходнике не доказывает, что импорты
  на сайте не работают. Отделяй стандартное поведение браузера от обработки Shikimori.
- Основа: четыре `main_code_*.css` E-design, дополнения истории и графика,
  CSS-club для расположения профиля и замены постеров, Google Fonts.
  Импортированные правила задают важные размеры, позиционирование и приоритеты.
- Не удаляй `!important`, нулевые отступы или повторные селекторы массово.
  Они могут переопределять импортированную тему. Проверяй конечный каскад.
- Новые фильтры используют `.c-ms`, `.c-ms-dropdown`, `.c-ms-option`,
  `.c-ms-option-mark`; выбранный пункт в присланной разметке имел класс `.is-on`.
- Шапка фильтров — `.b-collection-filters .c-filters-head`; ссылка сброса находится
  в `.misc-links`. Тема превращала эту область в круглые кнопки шириной 100%.
  Точечное переопределение уже убирает лишние псевдоэлементы и выравнивает текст.
  Боковые `margin: 4px` общего `.subheadline` здесь также сброшены.
- Реальный класс избранного — `.cc-favourites`. Содержимое достижений находится
  в `.achievements > .cc-2`; основной заголовок — отдельный `.subheadline`.
- В текущей разметке `.about.block > div` скрывает заголовок и кнопку редактирования,
  а содержимое TOP находится в `<center>` и остаётся видимым.
- Замены картинок используют псевдоэлементы, иногда с `z-index: -1`.
  Изоляция рисования и новые stacking context могут повлиять на их видимость.
- В старом CSS остались лишний `*/`, закрывающая `}` и `color: inhirit`.
  Не исправляй их попутно: восстановление ранее игнорируемого правила тоже может
  изменить оформление. Разбирай такие исправления отдельной задачей.
- Публичный исходный код Shikimori архивирован: сведения о восьмичасовом кэше CSS
  по URL и отсутствии рекурсивного разворачивания импортов требуют проверки на
  текущем сервере. Вложенные импорты пока не считаются проверенной схемой.
- При модульной миграции сохраняй порядок правил и учитывай относительные URL.
  Предпочтительны абсолютные импорты выбранного commit SHA, перечисленные прямо
  в редакторе. Перепаковка тех же правил сама по себе не ускоряет отрисовку.

## Публикация и безопасность

- Git push и PATCH профиля — независимые действия. На каждое нужно явное разрешение.
  Подтверждение относится к согласованному пакету изменений; не переспрашивай
  для уже одобренной отправки, но не распространяй её на новые правки.
- Используй проверенный процесс: локальная правка → diff и dry-run → подтверждение
  пользователя → публикация → повторный GET и проверка CSS.
- OAuth, обновление токенов и публикация — отдельные режимы скрипта. Не запускай
  авторизацию или refresh автоматически в dry-run.
- Документированный `GET/PATCH /api/styles/:id` проверен на собственном стиле.
  Форма текущего редактора при этом имела `action="/api/v3/users/styles/<id>"`.
  ID стиля и ID пользователя — разные значения; сверяй владельца через API.
- Сравнивай и резервируй поле `css`, а не `compiled_css`: второе содержит результат
  обработки импортов. Публикуй именно снимок, который был показан в diff.
- Скрипт проверяет аккаунт, владельца и отсутствие конкурентного изменения,
  сохраняет backup и не повторяет PATCH вслепую после таймаута.
- PowerShell 7+ обязателен. Если `pwsh` отсутствует в PATH, найди полный путь
  установленного исполняемого файла. Предупреждение PSReadLine само по себе
  не означает ошибку авторизации.
- `ConvertFrom-Json` в новых версиях PowerShell может возвращать дату объектом
  `DateTime`, а не строкой. В скрипте этот случай уже обработан и покрыт тестом.
- Токены и client secret вводятся только скрыто в локальном терминале.
  Не проси присылать их, callback URL с кодом или HTTP-заголовки в чат.
- Credentials защищены Windows DPAPI и находятся вне репозитория:
  `%LOCALAPPDATA%\ShikimoriCssDeploy\credentials.dpapi`; backups — рядом в `backups/`.
  Не выводи расшифрованные значения, ответы token endpoint и сырые HTTP-исключения.
- Тесты используют подставной API; проверка DPAPI может требовать доступа к профилю
  текущего пользователя Windows, недоступного из песочницы. Не подменяй её
  проверкой на реальных токенах.
- Не коммить локальную конфигурацию, `.dpapi`, `.env`, HAR, HTML страниц,
  записи Firefox, отчёты памяти и локальные копии изображений.

## Сохранённые эксперименты производительности

Наблюдения ниже относятся к сессии 24 октября 2026 года, а не к любому устройству.

- График активности: вместо изменения `height` и `margin` у 34 столбцов используется
  `profile-activity-pulse` с `clip-path` на псевдоэлементе. Цвета, задержки и пауза
  при наведении сохранены. Визуальная проверка пользователя пройдена.
- В сопоставленных участках покоя главный поток использовал примерно на 13% меньше
  CPU; при прокрутке убедительного выигрыша не было. Firefox выполнял `clip-path`
  вне композитора — не называй этот вариант полностью GPU-анимацией.
- `content-visibility: auto` оставлен по решению пользователя, хотя существенного
  выигрыша не подтвердил. Он применяется только от 1024px к `.cc-favourites`
  и `.achievements > .cc-2`. Начальные оценки высоты — 184px и 700px;
  после отрисовки `auto` запоминает реальные размеры. Основные заголовки снаружи.
- Визуальных побочных эффектов этих двух экспериментов пользователь не заметил.
- Прототип рамок через `transform` изменял свечение и скругления. Он отвергнут,
  не добавлен в рабочий CSS и не публиковался. Не восстанавливай его как готовую правку.
- Основная нагрузка включает декодирование анимированных WebP и отрисовку.
  Сокращение строк CSS не устраняет эти затраты. `animation-play-state` не ставит
  на паузу внутренние кадры GIF/WebP; `content-visibility` не гарантирует освобождение кэша.

## Как читать измерения

- Сравнивай одинаковые сценарии и показатели за секунду, а не суммы записей разной
  длительности. Покой, прокрутку и наведение рассматривай отдельно.
- Для базового сравнения: обновить страницу, дождаться загрузки и записать 10 секунд
  в одинаковом положении окна без прокрутки и движения мыши. Желательны повторы.
- В Firefox Profiler проценты справа могут относиться только к выбранному узлу.
  Отличай сэмплы, ожидание, CPU потока и загрузку всего процессора.
- При программном чтении новых профилей используй схему файла: родитель стека —
  `index - prefixOffset[index]`, ноль означает корень. Категория кадра значима
  только при `FrameFlag.HasCategory` (`flags & 4`), иначе наследуется от родителя.
- Выбирай главный поток активной вкладки через `activeTabID`, `pages.innerWindowID`
  и `usedInnerWindowIDs`: PID и индексы потоков меняются между записями.
- `Image Paint` с URL не измеряет полную стоимость изображения, декодирование
  или работу GPU. Частота этих маркеров не является рейтингом самых тяжёлых картинок.
- `about:memory` может дать память по URL. В одном снимке изображения занимали
  около 368 МБ, или 71,6% явных выделений процесса. TOP — около 134 МБ,
  избранное — 69 МБ, достижения — 58 МБ, франшизы — 47 МБ, два фона — 39 МБ.
  Это снимок кэша, не вся память Firefox и не рейтинг CPU.
- Разделяй сжатые данные (`source`) и декодированные поверхности. Числа в квадратных
  скобках отчёта памяти не принимай без проверки за полное число кадров файла.
  Вложенные суммы отчёта нельзя складывать повторно с их дочерними значениями.

## Локальный аудит изображений

- `.image-audit/` исключён из Git. Там находятся скачанные оригиналы, `inventory.json`,
  `downloads.json`, `results.json`, `report.md` и локальный анализатор `analyze.py`.
  Наличие этих файлов в следующем окружении не гарантировано; не публикуй их автоматически.
- Проверены 62 уникальных URL из основного CSS и `about.md`: 61 уникальный файл по SHA256,
  около 28,36 МБ скачанных копий, 2 609 кадров в учёте всех URL. Ошибок загрузки не было.
- Точных соседних повторов внутри циклов не найдено, в том числе после игнорирования
  RGB полностью прозрачных пикселей. Это не проверка на приблизительное сходство.
- У одной анимации совпали первый и последний кадры. Они не объединялись:
  такое изменение может сдвинуть начальную фазу и требует отдельной проверки времени.
- Анализ выполнялся по полным RGBA-кадрам после наложения и очистки. Новые версии
  изображений не создавались, ссылки и файлы на хостинге не менялись.
- Пользователь разрешил только сбор ссылок, скачивание копий и отчёт.
  Пересборка, загрузка оптимизированных версий и замена ссылок требуют нового согласования.

## Коммиты и дальнейшие изменения

- Делай отдельные коммиты для независимых структурных изменений: перемещения файлов,
  документация, скрипты и CSS не должны попадать в один большой несвязанный коммит.
- Не добавляй все файлы вслепую. Проверяй список staged-файлов, `.gitignore` и diff.
- Перед публичной публикацией новых материалов проверяй их на секреты и личные данные.
  Публичный CSS также не должен содержать секретных URL.
- До и после правок запускай проверки, соответствующие изменению: `git diff --check`,
  при изменении deploy — `tests/deploy.tests.ps1`, для оформления — проверку затронутых
  состояний в браузере. Не выдавай синтетический тест за проверку реального профиля.
- Сохраняй исходники и авторство сторонней темы. Переход на свою основу должен быть
  поэтапным и визуально проверяемым; фиксация импорта не равна его оптимизации.
