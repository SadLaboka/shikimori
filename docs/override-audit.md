# Оставшиеся переопределения: статический разбор

25 октября 2026 года. Основной CSS, четыре рабочих модуля, импорты и опубликованный
профиль не менялись. Это анализ, не проверка визуальной эквивалентности правок.

## Метод и пределы

Разобраны локальные `css/base/main_code_1.css` → main2 → main3 → main4,
затем пользовательская часть `styles_optimized.css` через существующий `prepareUser`.
Использован только локальный CSSOM Chromium в странице без сети, не предпросмотр сайта.
Инвентарь и анализатор: `.preview/override-audit/inventory.json` и `inventory.mjs`.
Эти локальные материалы не входят в Git.

Для автоматической части сравнивались только **одинаковые списки селекторов**
и **одинаковые условия** media/supports. Внутри такой группы учитывались
`!important` и порядок всех пяти файлов: раннее important также побеждает
позднее обычное объявление. Разные по специфичности/пересекающиеся селекторы
не объявляются эквивалентными автоматически; отдельные примеры проверены вручную.

Парсер разобрал 2 709 обычных правил, включая вложенные; keyframes/font-face
не считаются обычными правилами. Найдены 212 проигрывающих longhand-свойств
в 63 группах правил; 149 совпадают по значению с победителем. Это **не 212 строк
для удаления**: один `border` или `background` раскрывается в несколько свойств.
Дополнительно в 18 правилах повторяется один и тот же селектор внутри списка.

| Источник | Разобранные обычные правила | Проигрывающие longhand-свойства |
| --- | ---: | ---: |
| main1 | 508 | 140 |
| main2 | 700 | 33 |
| main3 | 544 | 20 |
| main4 | 724 | 16 |
| Основной CSS | 233 | 3 |

Базовые стили сайта и Google Fonts в этот инвентарь не входят. Расширенные
свойства/селекторы и запасные объявления могут по-разному разбираться Firefox:
например, `width: -moz-available` не отражает то же поведение в Chromium.
Поэтому числа служат для поиска кандидатов, а не разрешением массового удаления.

## Наиболее конкретные кандидаты

### 1. Повторный блок кнопки main1

В [main1](../css/base/main_code_1.css), строки 231–254, два `.b-link_button`.
Второй блок (247) повторяет `border`, `color`, `box-shadow` и обычный
`background-color`, уже заданный раньше с `!important`.
Между ними находится только `.b-link_button:hover`:

- Его `color`/`background-color` имеют большую специфичность и important,
  поэтому удаление второго обычного блока их приоритет не меняет.
- Его important `border: none` сильнее обоих обычных `border`.
- Промежуточного переопределения `box-shadow` нет.
- Длительность переходов и `border-radius` находятся в первом блоке и сохраняются.

Это хороший первый кандидат на удаление **целого второго блока**, после подготовки
проверяемой версии main1. Нужны реальные кнопки в обычном/hover/focus/active состоянии;
наличие их на профиле или каталоге пока не проверено, PASS компоненту не присваивается.

### 2. Полные и частичные повторы main3

- [main3](../css/base/main_code_3.css), 461 и 798:
  `.c-anime_video_episodes .b-show_more-more { display: inline; }` повторён
  без условий. Можно рассматривать удаление раннего блока, сохранив поздний;
  нужна проверка настоящего блока эпизодов, не только профиля.
- Там же, 1722 и 3511: ранний `.l-page { border-radius: 0px; }` перекрыт
  поздним `border-radius: 8px` у того же селектора без условий.
  Кандидат — только ранний `border-radius`; остальные свойства раннего блока нужны.
  Проверять профиль, историю и каталог, включая мобильные условия main4.
- Там же, 2061 и 2152: фон `body.p-achievements.p-profiles .l-page`
  сначала задан градиентом, затем сброшен `background: transparent`.
  Ранний фон статически перекрыт целиком, но нужна именно страница достижений.

### 3. Mobile: одинаковые записи, не исправление раскладки

В [main4](../css/base/main_code_4mob.css), строки 2188 и 2192,
внутри одного `max-width: 767px` два соседних одинаковых блока:

```css
body#profiles_show .profile-content { margin-top: -320px; }
```

Один можно рассматривать для удаления. Само значение `-320px` здесь не меняется:
чистка повтора не является исправлением мобильного дизайна. При реализации нужны
390/360 и граница 767/768. Другие мобильные переопределения, например 10px → 12px
у `header.head .notice`, не объединять с изменением дизайна.

### 4. Повторы внутри списков селекторов

Примеры: `.b-user.detailed` и `.buttons .item-delete-confirm:hover` в main1,
`.subheadline a[title="morr"]:hover:after` в main3,
`.userbox img.avatar, .userbox img.avatar` и `.profile-actions .talk:before` в main4.
Повтор одного и того же селектора в списке не увеличивает специфичность.
Оставление одного экземпляра — отдельный кандидат, без замены на `:is()`/`:where()`
и без изменения деклараций. Все 18 списков перечислены в локальном JSON.

## Что в основном файле сохраняем

- **Франшизы:** повторённый селектор `.cc-franchises .b-badge` в 1030 и 1146
  задаёт разные свойства: размер/отступы и позиционирование/кликабельность.
  Ни один из двух блоков не является целиком мёртвым. Объединение переместит
  декларации относительно промежуточных правил и требует отдельной проверки.
- **Фильтры:** цвет у dropdown, options и option — не доказанный дубль.
  Собственное правило дочернего элемента сильнее унаследованного цвета,
  даже если цвет у родителя important. Перед удалением нужно проверить также
  актуальные стили самого сайта и выбранные/hover/focus состояния.
- **График:** разные условия `@supports`, запасная анимация и параметры,
  наследуемые псевдоэлементом, не считать общим ненужным повтором.
- **Tooltip:** совместимость после q03 сохраняет приоритет `content` постеров.
- **Body:** shorthand `background` основного файла сбрасывает несколько свойств;
  три из них проигрывают important `background-size`/`background-position`
  из main1. Это не повод удалить весь `background`: его цвет и другие сбросы работают.
- **Переменные палитры и нулевые отступы:** совпадение отдельных значений основы
  не доказывает ненужность явных пользовательских настроек.

Небольшой собственный кандидат: `background-color: black` в media от 1280px
(строка 435) повторяет непосредственно предшествующий безусловный `body:after`
(428). Между ними нет другого объявления этого цвета; остальные три background
longhand в media цвет не сбрасывают. Удаление одной строки можно проверить
на 1279/1280 и обычных ширинах, но значимого ускорения от неё не ожидается.
Старые ошибки `*/`, лишняя `}` и `inhirit` не исправлялись попутно.

## Порядок дальнейшей реализации

1. Подготовить узкий процесс предпросмотра **изменённой** версии одного модуля,
   сохранив проверку опубликованного baseline, места импорта и неизменных правил.
   Сейчас owned-import путь намеренно принимает только байты vendor: изменённый
   main1 будет отклонён `assertVersionPinBytes` и привязкой manifest к upstream-хэшу.
   Просто изменить файл в `css/base/` или выключить проверку хэшей нельзя.
   Vendor и старые commit-URL остаются эталонами; для новой версии нужен новый URL.
2. Первый связный пакет — второй `.b-link_button` в main1, без прочих чисток.
   Выбрать реальную страницу с этой кнопкой и проверить состояния. Если кнопки
   нет в доступном анонимном DOM, явно оставить пробел и выбрать другой блок.
3. Следующий небольшой пакет — ранний радиус `.l-page` в main3, затем отдельные
   полные повторы. Mobile и страница достижений проверяются в своих сценариях.
4. При каждой правке: diff, синтаксис/семантика, отрицательный контроль,
   нужные ширины и состояния; публикация и push — только по отдельному разрешению.

Ни кандидатный CSS, ни сборщик, ни новая зависимость этим аудитом не создавались.
Визуальные тесты не запускались: пока нет CSS-изменения для сравнения.
Результат — список кандидатов и ограничений, не обещание ускорения или общий PASS.

Кандидат и точечный предпросмотр созданы отдельно; рабочий CSS не менялся.
На тестовых примерах различий нет, но реальных кнопок не найдено, поэтому
