# Выпуск личного расширения Firefox

Расширение распространяется как **Unlisted**: Mozilla проверяет и подписывает
его, без публичной карточки в каталоге. Готовые подписанные версии и файл
автообновлений хранятся в GitHub Releases этого репозитория.

## Первоначальная настройка

1. В кабинете Mozilla создай API credentials.
2. В **SadLaboka/shikimori → Settings → Secrets and variables → Actions** добавь
   `AMO_API_KEY` со значением **JWT issuer** и `AMO_API_SECRET` со значением
   **JWT secret**. Это именно секреты данного репозитория, не переменные.
3. Файл `.github/workflows/firefox-release.yml` должен находиться в `main`.
   Для ручной кнопки запуска GitHub требуется наличие workflow в основной ветке.
4. После первого успешного выпуска скачай подписанный XPI из GitHub Releases
   и установи через `about:addons` → ⚙ → «Установить дополнение из файла…».

Первый подписанный пакет 0.2.1 с адресом обновлений нужно установить вручную.
Предыдущие Unlisted-пакеты без этого адреса и временные дополнения не получают
данную настройку сами. Проверка обновлений Firefox периодическая; её можно
запустить вручную в менеджере дополнений. Мгновенная доставка не обещается.

## Новый выпуск

1. Измени код и повысь `extensions/firefox/manifest.json:version`.
   Для этого процесса используются три числовые части, например `0.2.2`.
2. Выполни проверки и обычный отдельный согласованный commit/push. Данный документ
   не даёт агенту разрешения автоматически отправлять изменения или CSS.
3. После попадания проверенного коммита в `main` создай и отправь **отдельную**
   отметку `firefox-v0.2.2` на этот коммит. Создание отметки — действие выпуска.
4. В GitHub Actions открой `Release Firefox extension` и дождись результата.

Workflow также можно запустить вручную, указав уже существующую отметку.
Нельзя указывать изменяемую ветку вместо отметки. Коммит проверяется на
принадлежность `main`, а номер — на точное совпадение с манифестом.

## Что выполняется автоматически

- Тесты расширения, выпуска, сборки CSS и проверки подписанного пакета.
- Сборка исходного ZIP из явного списка файлов, затем проверка Mozilla linter.
- Чтение указанной версии в AMO с краткоживущим JWT. Если её ещё нет — одна
  попытка отправки официальным `web-ext 10.8.0` в канал `unlisted`.
- Ожидание подписи до 15 минут. Даже после потерянного ответа версия повторно
  читается через API; существующая версия не отправляется заново.
- Получение только одобренного файла с AMO, сверка контрольной суммы API.
  Заголовок авторизации не передаётся CDN при перенаправлении.
- Сверка всех исходных файлов внутри подписанного XPI с исходным ZIP, включая
  имена с учётом регистра. У `manifest.json` разрешено только форматирование
  и порядок ключей при полном совпадении JSON-полей и значений; остальные файлы
  сравниваются побайтно. Допускаются дополнительные файлы `META-INF`
  подписи Mozilla. Это проверка неизменности полезной нагрузки; доверие к
  происхождению обеспечивают API Mozilla, HTTPS и опубликованная им сумма файла.
- Публикация `shikimori-schemes-<версия>.xpi` в отдельном выпуске
  `firefox-v<версия>`. Файл существующей версии другими байтами не заменяется.
- После появления XPI переключение `updates.json` в служебном выпуске
  `firefox-updates`. Файл содержит точную версию, ссылку и SHA512.

Постоянный адрес обновлений:
`https://github.com/SadLaboka/shikimori/releases/download/firefox-updates/updates.json`.

Старую версию поверх более новой процесс не публикует. Перед сменой списка
обновлений новый файл загружается под временным именем, старый сохраняется как
`updates-backup-<id>.json`. Если переименование нового файла не удаётся, процесс
пытается вернуть старому имя `updates.json`. Во время смены имени возможна
короткая недоступность адреса; старые установленные расширения продолжают работать.

## Если Mozilla рассматривает версию дольше

Не повышай номер и не пересоздавай отметку только из-за ожидания. Проверь состояние
версии в Developer Hub. После одобрения повторно запусти workflow с **той же
отметкой**. Он сначала найдёт существующую версию и продолжит получение файла.
Если версия отклонена, внеси требуемые исправления и выпусти новый номер.

Если версия не найдена и прежняя отправка завершилась неопределённо, сначала
проверь кабинет Mozilla: автоматических повторов записи в рамках одного запуска
нет. API и имена файлов могут измениться на стороне сервиса — ошибка останавливает
выпуск до изменения списка автообновлений.

Если остановка произошла после публикации XPI, проверь оба выпуска GitHub и
`updates.json`. Повтор того же выпуска допускается при совпадающих файлах.
Отметки выпущенных версий не перемещай; содержимое версионных XPI не меняй.

## Локальные проверки без ключей и отправки

```powershell
node --test tests/firefox-extension.test.mjs tests/firefox-rate-limit.test.mjs tests/firefox-avatar.test.mjs tests/build-css.test.mjs tests/firefox-release.test.mjs
pwsh -NoProfile -File tests/verify-firefox-signed.tests.ps1
node scripts/build-css.mjs --check
node scripts/build-emerald-scarlet.mjs --check
pnpm --dir tools/firefox-release install --frozen-lockfile --ignore-scripts
pnpm --dir tools/firefox-release exec web-ext lint --source-dir ../../extensions/firefox --self-hosted --no-config-discovery
```

`package-firefox-extension.ps1` создаёт неподписанный пакет. Сам запуск сборки,
тестов или linter ничего не отправляет Mozilla. Живой Shikimori в процессе
выпуска не участвует; его OAuth, токены и публикация CSS не используются.

Проверялся Firefox для компьютера. Linter 10.8.0 сообщает предупреждение о
Firefox Android 140 и разрешениях сбора данных; работу на Android эти проверки
не подтверждают. Desktop Firefox 140+ оставлен без изменения требований.

## Демонстрация в README

`docs/images/firefox-theme-switch.webp` — запись настоящего расширения в отдельном
Firefox 159 на копии публичной страницы. Запись выполнялась с тестовым API:
сохранения перехвачены, CSS живого профиля не менялся. Это демонстрация интерфейса,
не измерение скорости настоящей публикации. В анимации есть соответствующая подпись.
Исходные кадры и технические отчёты находятся в игнорируемой `.preview/`.
